## 3 声明：`materials:`

写在产出方的 ASSET.yml 里，可选。没有这个字段，就是这个组件不给炉子供料。

```yaml
materials:
  - id: decisions                 # 组件内唯一；小写字母、数字、短横
    title: 拍板账                 # 人读名
    kind: decision                # 正本口写一个 kind；派生口可以写一组：[decision, profile]
    tier: canon                   # canon 正本口 | derived 派生口
    read: [materials.py, decisions]   # 读数命令，规矩同 FACES-SPEC 第 3 节的 read
    ttl: 300                      # 炉子缓存读数的秒数，缺省 300
```

- **炉子只凭声明就能建委派链，不跑任何读数。** 哪个 kind 有哪些口、谁是正本，全写在声明里。这就是「扫元数据 ≠ 建对象」。
- `read` 的规矩照 FACES-SPEC 第 3 节：只许组件目录里的 `.py`，不许 shell；炉子只跑声明里写的命令。
- **正本口和派生口怎么分**（他拍第 4、5 条）：
  - 正本口：这条料本身住的地方。改它，就是改了这条料。
  - 派生口：从别处算出来的副本或计数。丢了能重算。
  - 判据只看「丢了能不能重算」，不看它是文件还是库。多数时候正本恰好是文本，但个人总账那种 SQLite 就是正本。
- **「正本」只说这条料住哪，不说它审没审过。** 画像台账对炉子是正本口，可它里面装的是机器起草的候选，不是画像正本（memory 里的 `user_*` 卡）。审没审过，放进 `extra.mark` 照原样带过来。

### 3.1 为什么不和 `projections:` 并成一种声明

1. **Spring 本来就分开写。** 一个类一份元数据，上面可以挂 `@Controller`、`@Repository` 几种注解。每种处理器只读自己那种，共用的是底下 `@Component` 那层规矩。对过来：一张 ASSET.yml，两种声明键，两个消费方各读各的键。共用的是读数口规矩（FACES-SPEC 第 3 节 `read`、第 4 节）。
2. **合并的代价现在换不来东西。** 已有 9 张卡写了 `projections:`。合并要改这 9 张卡、书桌 `faces_api.py`，还要把书桌升到 `faces/v1`。
3. **两个消费方各升各的版本。** 料的形状改了，不该逼着书桌升版。
4. **「一份元数据，多个消费方」另有一条路。** 料的形状是统一的，书桌以后可以把任何 `materials:` 自动画成一块收件箱前端件，像身份件那样不用另写声明。记在第 13 节负空间。
5. 读数口规矩出现第 3 个消费方时，再从 FACES-SPEC 抽进 ASSET-CARD-SPEC，单成一节（沿用「同类第 3 次」）。

## 4 读数口的规矩

1–4 条同 FACES-SPEC 第 4 节：stdout 只有一份 JSON 对象；只读；没读到写 `null`，不写 0；20 秒内跑完。另加四条：

5. **不替炉子筛。** 「被 ≥3 场撞回才算候选」是炉子的判断，读数口照实全吐。条目太多可以截，截了要在 `note` 里写截了多少。这是炉子的老红线：截断要看得见，不许静默。
6. **只靠标准库和 PyYAML。** 炉子用它自己的 python 跑读数口，同书桌。
7. **派生口只吐落在该 kind「单位」里的条目**（单位见第 5.1 节）。`ptr` 写正本的位置，不写派生库自己的位置。
8. 读数脚本的文件头照 toys `capability-contract/SPEC.md` 写「用于 / 产出 / 成功 / 不用于」四个字段。声明里不重复写。

## 5 料的形状（`intake/v0`）

读数口吐：`{"items": [料, …], "asof": "...", "note": "..."}`。`note` 是这份读数的限定语，炉子**必须显示**，不能藏。

| 字段 | 必有 | 类型 | 含义 | 通常谁给 |
|---|---|---|---|---|
| `id` | 是 | string | `<kind>:<16 位十六进制>`，算法见第 5.1 节。同一份料在所有存储里必须同 id | 都给 |
| `kind` | 是 | string | 料的种类，词表见第 5.1 节 | 都给 |
| `text` | 是 | string，≤240 字 | 一句话：这条料讲什么 | 正本口 |
| `ptr` | 是 | string | 正本在哪。文件写 `<本机绝对路径>#L<行>`；库写 `<库的绝对路径>#<表>.<键>`。派生口也写正本的位置 | 都给 |
| `ts` | 键必有，值可 `null` | ISO 日期或日期时刻 | 这条料立下的时候（不是被撞回的时候） | 正本口 |
| `quote` | 可缺 | string | 原话锚：他当时那句原话 | 正本口 |
| `count` | 可缺 | int | 立下以后，被几场别的会话撞回（立它的那场不算） | 派生口 |
| `seen` | 可缺 | `[{sid, date, title?}]` | `count` 数的是哪几场 | 派生口 |
| `extra` | 可缺 | object | 产出方自带的附注。炉子不解读，只在详情里原样显示 | 正本口 |

- `ptr` 写绝对路径：炉子在另一个仓，toys 的仓内相对路径对它没有意义。
- 框题草案的 `evidence`（原话或场次）拆成了 `quote` 和 `seen` 两个字段（④）。理由：原话管「验得动它是真判断还是漂亮话」（README 第 3 句），场次管「count 查得到」；一个字段有时是字符串、有时是列表，炉子就得猜类型。
- `count` 只有一个意思：被之后的会话撞回的场数。别的计数（比如画像簇里有几条观察）放进 `extra`，不借用 `count`。
- `extra` 是加的（④）：拍板账的 why、排除、节点，画像的簇名、审定标记，都有地方放，最小形状不用为每种料加字段。

### 5.1 kind 词表 v0

| kind | 叫法 | 单位（一条料是什么） | 正本 | id 正文 | `ts` 取 | `quote` 取 | 命名空间 | 已知派生 |
|---|---|---|---|---|---|---|---|---|
| `decision` | 拍板 | `DECISION-LEDGER.md` 里一行 `- YYYY-MM-DD \| …` | toys `DECISION-LEDGER.md` | 整行，含行首 `- ` | 行首日期 | 第一对「」里的话 | `decision-ledger` | `judgment_hits.db` |
| `profile` | 画像候选 | `profile-ledger.jsonl` 里一条 `event: member` | toys `my-desk/harvest/semantic-candidates/profile-ledger.jsonl` | observation、evidence_quote、cluster_title、draft、reason 里是字符串的，依次空格拼起来 | `date` | `evidence_quote` | `profile` | `judgment_hits.db` |
| `insight` | 提炼候选 | `INGEST-QUEUE.md` 里一行 `- …` | toys `INGEST-QUEUE.md` | 整行，含行首 `- ` | 行尾 `\| YYYY-MM-DD` | — | `ingest` | `judgment_hits.db`（v0 没有正本口） |
| `kg` | kg 段 | kg 文件里的一段（YAML 按顶层键和第一层条目切，md 按 1–3 级标题切） | knowledge-graph 仓 | 段正文 | `null` | — | `kg` | `judgment_hits.db`（v0 没有正本口） |

**id 算法**：`<kind>:` 加上 `sha1("<命名空间>\n<id 正文，空白归一>")` 的前 16 位十六进制。

- 命名空间沿用 `judgment_hits.db` 已经在用的源名。这样库里现有的 key 不用重算，就和正本口对得上（现行实现是 toys `session-archaeology/live_session.py` 的 `_entry_key`）。
- 同一个 kind 的所有口必须用同一个算法。算法以本表为准，代码照表写；对不上，改代码。
- 代价：正文改一个字，id 就变了，派生库里的旧 id 会变成 `stale`。这是对的：那条判断确实改过了。
- 加 kind 算档 3：做完口头报一句，在本表加一行（同 FACES-SPEC 加版型）。

## 6 委派：同一份料在两处时，谁说了算

他拍的是「先找正本，再看派生」。双亲委派的原意是：先问上层，上层找得到就用上层的，下层不许顶替。照搬到「整条料」会出问题：正本里有这条，炉子就不再问派生口，撞回计数就丢了。而计数恰好是这批料的用处。所以**委派落到每个字段上**：

1. **建链（不跑读数）**：按声明给每个 kind 排一条链，正本口在前，派生口在后。
2. **跑读数**：先跑正本口，再跑派生口。
3. **按 id 合并，每个字段先问正本**：正本口给了这个字段（键在、值不是 `null`），就用正本的；没给，才用派生口的。
   - 效果：`text`、`ptr`、`ts`、`quote` 几乎总是正本说了算，派生口顶替不了；`count`、`seen` 正本口不给，就由派生口补上。
4. **条目在不在**，分四种状态：

| 状态 | 什么时候 | 炉子显示 |
|---|---|---|
| `ok` | 正本口里有这个 id | 正常显示 |
| `stale` | 正本口这次读成功了，但里面没有这个 id，只有派生口有 | 「正本里找不到了：改过字，或者被收割走了」 |
| `unverified` | 正本口这次没读成（脚本报错、超时） | 「正本没读到，没核过」。**不许因为正本口坏了，就把派生口的料全判成 stale** |
| `alone` | 这个 kind 根本没声明正本口 | 派生口单独作答，不另标 |

5. 合并后每条料多带两个字段：`via: {canon: "<组件>/<口>", derived: "<组件>/<口>"}` 和 `state`。

**v0 的限制**：

- 每个 kind 至多一个正本口、一个派生口。多出来的报进 `problems`，不进链。
- 两个派生口谁先，等第二个派生口真出现（多半是向量库上线时）再定。
- 同一个 id 出现在两个正本口里，是声明错了（一份料只有一个正本），报进 `problems`。

## 8 回炉单（`charge_sheet.py`）怎么办

**判断：并列，不替换。**（④）

- 回炉单读的是 hook 路由台账和会话转写：每条开口命中了哪些路由，按组件、按「事」归集。这些是**痕迹**，不是成形的料。
- 硬塞进第 5 节的形状，`matched`、`sid` 只能夹在 `extra` 里，炉子就得去解读 `extra`，破了约定。
- 它和 `judgment_hits.py` 是同一层：读上游痕迹，算出派生的东西。所以它是炉子**自己的一个生产者**，不是进料口。

三处变化：

1. **改名定位**：`docs/charge-sheet.md` 的标题从「炉子的进料口」改成「炉子自己的攒料器」，在那份文件里留黑匣子（第 0 节第 2 条）。
2. **会话来源改走侠客花名册**（档 2）：`charge_sheet.session_glob` 只指 toys 的 Claude 槽。09-14 花名册上线后，Codex 的卷宗和别的项目槽都进不来。`heroes/` 本身就是「加一位侠客 = 加一个模块、挂个名」的登记机制，回炉单该用它。
3. **以后**：回炉单的产出（开场 miss 区：该有设计到场、却裸奔的开场）在 reflect-forge 自己的 ASSET.yml 里声明成料（kind `miss`），炉子自己攒的料也走同一条扫描进料。Spring 自动配置里，框架自带的 bean 也走同一条登记路。要先让 reflect-forge 进 `roots`、补一张卡。不进首批。

台账路径 `charge_sheet.ledger_path` 暂时留在配置里，算不算违反第 1 条，第 11 节问他。

## 9 首批接入：session-archaeology 一张卡、三个口

```yaml
materials:
  - id: decisions
    title: 拍板账
    kind: decision
    tier: canon
    read: [materials.py, decisions]
  - id: profile
    title: 画像候选
    kind: profile
    tier: canon
    read: [materials.py, profile]
  - id: judgment-hits
    title: 被撞回的旧判断
    kind: [decision, profile, insight, kg]
    tier: derived
    read: [materials.py, judgment-hits]
    ttl: 900
```

**为什么三个口都由 session-archaeology 声明**（④）：正本口和派生口的 id 算法必须一字不差，现成的实现只有一份（`live_session.py` 的 `_line_entries` 和 `_entry_key`），放在一个组件里才不会漂。

- 这是对 FACES-SPEC「数据归谁谁声明」的一处有意偏离：拍板账住 toys 仓根，没有组件目录；画像台账是 dispatch-kernel 的运行态，文件却住在 my-desk 下面。
- 哪天别的组件要自己声明这些口，先按第 5.1 节把 id 算法对一遍。

| 口 | 读什么 | `text` | `quote` | `ts` | `count` / `seen` | `extra` |
|---|---|---|---|---|---|---|
| `decisions` | `DECISION-LEDGER.md` 里每行 `- YYYY-MM-DD \|` | 「——「」前面那句拍板 | 第一对「」 | 行首日期 | 不给 | why、排除、节点、源；机器补记行尾的「默认通过，非他过目」放 `mark` |
| `profile` | `profile-ledger.jsonl` 里 `event: member` 的行 | `observation` | `evidence_quote` | `date` | 不给 | `cluster`、`cluster_title`、`ws`、`sid`、`mark` |
| `judgment-hits` | `judgment_hits.db`，只读打开 | 库里的展示正文 | 不给 | 库里的 `entry_date` | `count` = 撞回的不同场数；`seen` = 那几场 | `same_day`：其中几场是同一天 |

要顺手改的两处：

- `judgment_hits.top_rows()` 现在只带出场的标题，要加 sid 列表，`seen` 才有 sid。
- `judgment-hits` 口要丢掉画像台账里非 `member` 行的命中（库里索引了全部行）。画像台账只追加，按行号回读那一行看 `event` 就行。它吐全部 `count ≥ 1` 的条目，不像前端件那样只吐 ≥2 的。

## 10 红线与演进

- **炉子不存第二份事实**：料只从读数口来，`data/` 里不存料的副本（读数的内存缓存不算）；炉子只记自己的加工状态。
- **炉子只跑声明里写的命令**；请求里只收 `kind` 和 `min_count`，不收命令、路径。
- **`roots` 就是信任边界**：加一个根，等于信它目录里的脚本。clone 来的外部仓不进 `roots`。
- **公网演示关掉进料**：`FORGE_DEMO=1` 时两个接口都不扫本机；`scripts/export_static.py` 不抓 `/api/intake/*`。料里是他的拍板原话，不能进 `site/`。
- **改料的形状 = 升 api**（`intake/v1`），并给旧形状一条转换。**加 kind = 档 3**，做完报一句。

## 13 负空间（v0 没做的）

- **消费设计没做**：料在炉子哪里显示（寻料页加一区，还是回炉单加一节）；料怎么变成铁去锻剑。没有 `quote` 的料（kg 段、提炼候选）能不能直接锻，还是得先入反思炉，也在这一场定。
- 书桌把 `materials:` 自动画成前端件（第 3.1 节第 4 条）。
- 画像正本（memory `user_*`）不是首批 kind。要进，就另立一种 kind，`text` 是并进画像的那句话。
- kg 自己的拍板账（kg `meta/decision-ledger.md`）要是当 `decision` 的第二个正本口，会撞上第 6 节「每个 kind 一个正本口」的限制。那时放开成「可以有多个正本口，id 不许重」，命名空间也得另起。
- 09-01 用磨分离框题的切片 2「兵器架全组件登记」，可以复用本件的扫描器：扫卡本身就是登记。
- 两台 Mac 上 `roots` 的路径不同，靠各自的 `config.json`，不进约定。
- id 要不要换算法（比如向量库要按语义认同一条），等第二个派生口出现时一起看。
